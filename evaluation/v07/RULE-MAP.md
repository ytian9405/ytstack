# v07 规则对照

三个新技能里的每条规则，对应 `voice/PREFERENCES.md` 的原文短句，或标明没有偏好依据。技能正文不写评测题里的具体名词。

## teach

| 规则 | 依据 |
| --- | --- |
| 讲到用户真懂：是什么、怎么运作、为什么做成这样。 | “讲机制时把用户当小白。术语当场翻成人话，讲不清就举例。” |
| 只做只读操作：读文件，git log、git blame、git show，以及不改状态的命令。不写文件，不删，不联网发送，不花钱。会改数据的命令不跑，改用读代码讲。 | “放权时写明红线。写清哪些只读、哪些不许动；花钱、删除、合并之前先说一句。” |
| 自己读代码和 git 记录。不派子代理。 | 不派子代理：任务要求的改写，无偏好依据。上游 teach 要派子代理。 |
| 触发要带对象，例如“讲讲 X 是怎么工作的”“为什么 X 要这样”。“为什么要这样设计”也算，不必再点名对象。单独的“讲讲”不算。上一条的“听不懂、看不懂、说人话、什么意思、我没太明白、我不太理解”归 bro。“听不懂，X 是怎么……的”归 teach。 | “看不懂会直说。”“讲机制时把用户当小白”管的是机制本身，不是改写上一条回复。v07 触发漏了“为什么要这样设计”。 |
| 从对话判断用户为什么问、已经懂什么。不要反问考用户。挑两三件该带走的，跳过已经懂的。 | “先给一段人话摘要。”“不重复解释。”不要反问：上游做法，无偏好依据。上游 teach：“not quizzed out of them.” |

## v08 改动

依据是 `voice/PREFERENCES.md` 的原文短句，或 v07 REPORT、MODEL-METRICS 的触发部分。技能正文没有写某道题里的名词。

- **ketchup 交接。** 主体改成能照着做的编号步骤，每步一两句，同一件事不在每节里再讲。目的有用户确认过的复述才整段用，否则一两句概括，不贴用户原话。写清没提交的改动、git 外的数据文件、正在跑的后台任务（怎么查状态、产出在哪），以及新机器上的第一步。写完后的回复改成几行：文件在哪，要带走或另外处理什么，最要紧的下一步，几件等用户定。依据：v07 REPORT 的 H1；“交接说明只写必要的事实和基本指引”“停在概括时要给具体步骤”“不重复解释，不写交代性的套话”“派活时写清每步怎么算完成”。
- **ketchup 触发。** description 最前面写明：把活交给或派给另一个 agent、Codex、worker 去做，归 orca-cli，不要读本技能。回来汇报的触发说法加上“有什么要我定的”。依据：v07 REPORT 和 MODEL-METRICS 的触发部分。误触发是“把这活交给另一个 Codex”“handover 给另一个代理”；漏触发是“有什么要我定的”。
- **teach。** 比方最多一句，帮新手抓住大意，紧接着回到项目里真实的一次操作，比方不能代替真实例子。有容易误解的地方单独点出来，并说后果。触发说法加上“为什么要这样设计”，不必再点名对象。依据：v07 REPORT 的 T1；“讲机制时把用户当小白。术语当场翻成人话，讲不清就举例。”“写短时别删理由。”触发漏项见 REPORT 和 MODEL-METRICS。
- **in-your-own-words。** 去掉“3 到 5 句”。一条独立的事占一个列表项，按事情条数写。开头可以有一句总括。用户自己的猜测单列并标成猜测。用户说了先别定的事单列。整体仍然短，不写计划。点名调用的开关不改。依据：v07 REPORT 的 I1；“一条独立的信息占一个列表项。”“结论要有出处，不许猜。”“方向和取舍由用户定。”
