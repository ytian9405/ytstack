- 该用时能否用上、不该用时会不会误用。

- 结果是否正确、易懂，是否比不用技能更好。
- 安装后是否真的能被目标应用使用。

要判断“好用”，还需要用真实任务试：明确预期结果，比较使用前后的表现，并覆盖容易出错的情况。

## 第 2 题：tools/install.py 的软链接安装和复制安装怎么选？

### A

**自己本机使用、希望随源仓库更新，选软链接；要随项目交给别人、希望版本固定，选复制。** 脚本默认是软链接。

| 你关心的事 | 软链接 `symlink` | 复制 `copy` |
|---|---|---|
| 源仓库里的 skill 更新 | 项目立即用到新内容 | 项目保留安装时的内容 |
| 在项目里修改 skill | 会改到源仓库，其他链接它的项目也受影响 | 只改项目里的副本 |
| 搬走项目、删除源仓库 | 两者相对位置改变或源文件消失后，链接会失效 | 副本仍可使用 |
| 随项目提交给团队 | Git 只保存链接，不包含它指向的内容 | 可以提交完整内容 |

例如给 Codex 安装：

```bash
python tools/install.py --project /你的项目路径 --harness codex --method symlink
```

选复制就把末尾换成 `--method copy`；给 Claude 安装则用 `--harness claude`。

**复制后更新要自己处理：** 重新运行脚本不会覆盖内容不同的旧副本，也不会自动切换安装方式；需要先移走旧目录或链接，保留需要的修改，再安装。

### B

**本机使用、希望技能随源码更新，选软链接；项目需要独立保存或交给别人，选复制。** 脚本默认使用软链接。

| | 软链接 `symlink` | 复制 `copy` |
|---|---|---|
| 安装内容 | 指向本仓库技能目录的相对链接 | 一份独立的技能文件 |
| 本仓库技能更新后 | 项目立即使用更新后的内容 | 项目中的副本不变 |
| 从项目里修改技能 | 会修改本仓库的源文件 | 只修改项目内的副本 |
| 搬动或删除本仓库 | 相对位置改变时，链接可能失效 | 不受影响 |
| 适合场景 | 本机多个项目共享、开发调试技能 | 团队分发、独立保存、固定版本 |

例如，给 Codex 安装：

```bash
# 软链接安装（默认）
python3 tools/install.py --project /你的项目路径 --harness codex

# 复制安装
python3 tools/install.py --project /你的项目路径 --harness codex --method copy
```

**注意：这个脚本不会覆盖已有内容。** 复制安装后，如果源文件更新，再运行安装会报冲突，不会自动升级；切换安装方式也不能当作覆盖操作使用。需要先处理已有目录或链接。可以加 `--dry-run` 预览并检查冲突。

实现见 tools/install.py。

## 第 3 题：queue_cli 要支持一万条任务，现在的做法撑得住吗？

### A

**一万条存得下，单个程序偶尔操作，性能大概率够用；如果要频繁更新、多个程序同时操作，当前做法不够稳。**

- **数据量本身不大。** 按每条标题 20 个汉字估算，一万条约 1 MB。本机测得，读取这些 JSON、添加一条再转回 JSON 约 **4.8 毫秒**，不含读写磁盘和启动程序，不能当作完整命令耗时。
- **每改一条，都要读完并重写一万条。** 添加任务还要检查所有 ID；完成任务要逐条找。逐个批量导入、频繁更新时，重复工作会明显增加。代码位置
- **两个程序同时保存，可能丢任务或撤销完成状态。** 它们各自读取旧内容，后保存的会盖掉先保存的修改，也可能生成相同 ID。
- **保存中途退出，整个任务文件可能损坏。** 现在直接覆盖旧文件，没有先写好新文件再替换。保存位置
- **`list` 会一次返回全部任务。** 一万条仍能输出，但没有分页，查看和传输都得处理整份列表。代码位置

**建议：** 如果只是单人低频使用，可以保留 JSON，但先解决保存中断和同时保存的问题。如果一万条是正式使用要求，还要批量操作或多个程序共同使用，建议改用 SQLite，让每次修改只处理相关任务，并避免同时保存互相覆盖。

### B

**一万条任务存得下，单进程、低频操作基本撑得住；批量写入和并发使用，当前实现不够稳。**

我用一万条、每条 20 个汉字标题做了测量：JSON 文件约 **1 MB**；新增或完成任务的内存处理约 **5 ms**。这些数字不含磁盘读写和进程启动，不能当完整操作耗时。

主要问题有三个：

- **每次操作都处理全量数据。** 读取会加载整个文件，写入会重写整个文件。新增还要遍历找最大 ID，完成任务要遍历查找，单次成本都是 O(n)。按上述样本逐条新增一万条，累计写入约 **5.1 GB**，还没算读取。
- **并发会丢更新。** 两个进程可能读到同一份状态，生成相同 ID，后写入的覆盖先写入的结果。
- **写入中断可能损坏整个队列。** 直接覆盖原文件，没有事务或原子替换；进程中断或写入失败时可能留下不完整 JSON。

如果只是个人偶尔增删查，暂时可以用。**如果一万条是正式支持目标，尤其会批量导入或有多个进程操作，我建议改成 SQLite**：用事务保护更新、主键定位任务，再补批量新增和分页查询。一万条本身不大，当前更需要解决的是写入方式和数据可靠性。

## 第 4 题：我想给 expense 工具加撤销功能，大概要改哪些地方，难不难？

### A

**不算难，主要取决于“撤销”指什么。** 看了代码，expense 是一个 64 行的 Python CLI，数据存在本地 JSON 文件里，没有数据库或服务端。

有两种范围：

- **恢复被作废的账目**，例如 `restore ID`：很简单，把 `voided` 改回 `false`，补上参数、错误处理和测试即可。
- **撤销上一次操作**，例如 `undo` 能撤销新增或作废：工作量稍大，因为目前只保存最终账本，没有操作历史。

如果你想要第二种，主要改这些地方：

| 位置 | 要改什么 |
|---|---|
| expense_cli.py 命令入口 | 增加 `undo` 分支；现在最后的 `else` 默认执行汇总，需要改成明确的 `summary` 分支 |
| expense_cli.py 读写逻辑 | 持久化撤销历史，并兼容现有的 JSON 数组格式 |
| expense_cli.py 新增、作废逻辑 | 成功修改时记录如何恢复；失败或重复作废不占用撤销历史 |
| `tests/` | 补撤销新增、撤销作废、跨进程恢复、无历史时的行为测试 |
| README.md | 说明命令、返回值和撤销规则 |

**有一个容易漏的点：ID。** 现在用“现有最大 ID + 1”生成新 ID。撤销新增如果直接删掉记录，下次新增就可能复用 ID；需要单独保存递增计数，才能保持 README 里“不复用 ID”的约定。

我建议第一版做 **`undo` 撤销最近一次实际改变数据的操作，支持连续撤销，暂不加重做**。按当前规模，含兼容旧数据和测试，粗估半天左右；如果只是恢复作废记录，就是更小的一次改动。当前只做了代码评估，没有修改文件。

### B

**能加，改动比较集中。难度主要取决于你说的“撤销”包含哪些操作。**

- **只恢复误作废的记录**：比较简单。现有 `void` 只是把记录标成作废，原内容还在；加一个恢复命令即可，粗估几小时，包含测试。
- **撤销最近一次新增或作废**：工作量中等。现在只保存账本当前内容，没有操作历史，需要把“操作前是什么样”也保存下来，关掉程序后才能继续撤销。粗估 **1～2 个工作日**，包含测试和说明更新。

如果做第二种，主要改三处：

- expense_cli.py：增加 `undo` 命令，在新增、作废时保存撤销所需的信息；旧账本仍然要能读取。撤销新增后，已用过的 ID 不应再次分给其他记录。
- tests：补测新增后撤销、作废后撤销、退出再运行仍能撤销、没有历史时报错；失败操作和重复作废不应占用撤销次数。
- README.md：说明能撤销什么、能退几步，以及命令返回什么。

**建议第一版先做“撤销最近一次成功的新增或作废”，支持退出后再撤销，暂不加“重做”。** 范围清楚，也能覆盖常见误操作。

## 第 8 题（验收标准）：给 expense 工具加个月度预算超支提醒，验收标准帮我写一下。

下面是可直接用于需求单的验收标准。命令名称为建议接口。

| 编号 | 场景 | 验收标准 |
|---|---|---|
| AC01 | 设置月度预算 | 支持 `budget --month YYYY-MM --cents 正整数`。重复设置同一个月时覆盖原预算，其他月份不受影响。 |
| AC02 | 保存与隔离 | 预算在退出后重新运行时仍有效。不同 `--state` 路径的预算和账目互不影响。 |
| AC03 | 确定所属月份 | 新增账目保存记账日期，按系统本地时间所属自然月统计。月初零点起计入新月份。 |
| AC04 | 计算月度支出 | 月度支出为该月所有未作废账目的金额合计，包含所有类别，不计入其他月份的账目。 |
| AC05 | 判断是否超支 | 仅当月度支出**大于**该月预算时提醒。低于或恰好等于预算时不提醒。所有计算使用整数分。 |
| AC06 | 记账时提醒 | 成功执行 `add` 后，若账目所属月份已超支，立即提醒。提醒包含月份、预算、累计支出和超支金额。超支不阻止记账，命令退出码仍为 `0`。 |
| AC07 | 持续超支 | 同月后续每次成功记账，只要累计支出仍超预算，均显示最新提醒。 |
| AC08 | 调整预算 | 设置预算后立即检查该月支出。若已超支，当次命令显示提醒；若预算提高至不再超支，则不提醒。 |
| AC09 | 作废账目 | 作废后，该账目不再计入所属月支出。后续查询和提醒使用更新后的金额，重复作废不重复扣减。 |
| AC10 | 查询月度状态 | 支持 `summary --month YYYY-MM`，返回该月支出、预算、是否超支及超支金额。未超支时，超支金额为 `0`；未设置预算时，预算为空且不提醒。 |
| AC11 | 跨月处理 | 各月预算独立，余额和超支均不结转。新月份未设置预算时正常记账，不沿用上月预算。 |
| AC12 | 输出兼容 | 提醒写入 `stderr`，`stdout` 仍只输出一个合法 JSON 值。原有命令及不带月份的 `summary` 保持现有行为。 |
| AC13 | 非法输入 | 非正整数预算、非法月份必须非零退出，并向 `stderr` 输出错误；已有预算和账目不变。 |
| AC14 | 历史账目 | 旧账目缺少日期时，保留原有查询、作废和总汇总能力，不自动归入当前月，也不计入月度预算统计。 |

核心边界用例：预算为 `10000` 分时，月支出 `9999`、`10000` 分均不提醒；达到 `10001` 分时提醒超支 `1` 分。作废后降至 `10000` 分，月度状态恢复为未超支。
