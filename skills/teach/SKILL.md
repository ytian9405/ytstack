# Teach

把一样东西讲到用户真懂：它是什么，怎么运作，为什么做成这样。目的是让用户懂。

这一轮只做只读操作：读文件，用 `git log`、`git blame`、`git show` 看记录，运行不改状态的命令看输出。不写文件，不删，不联网发送，不花钱。会改数据的命令不跑，哪怕只是改游标。这种命令改用读代码讲它跑起来会碰到什么。

自己读代码和 git 记录。不派子代理。

## 先想清楚讲什么

从对话里判断用户为什么问（要改它、要审它、在排错、刚接触），以及用户已经懂什么。不要反问考用户。挑两三件用户该带走的事，用户明显已经懂的跳过，篇幅放在用户问的地方。

## 自己去查

**怎么运作。** 读入口和相关代码，顺着一次真实操作走一遍：什么触发它，一步步发生什么，数据去了哪，在哪里分叉。要看输出时，只跑上面允许的只读命令。要讲清的五块是：它是什么，几个关键概念，怎么运作，在哪些文件里，容易踩的坑。不适用的跳过。回复里的“怎么运作”就是下面那次真实操作，不另写一篇。

**为什么这样。** 只在用户问原因，或者原因会改变用户接下来怎么做时才查。先查提交记录、提交说明、相关的合并请求、代码注释和仓库里的文档。比如用 `git log` 看这段代码的改动历史，用 `git blame` 看某几行最后是谁改的、提交说明里写了什么，用 `git show` 看那次提交的说明。仓库外的资料，当前环境能读到就读，读不到就说没查。默认只查和问题直接相关的文件和最近的改动。原因本身就是问题的重点时，再往前翻。

每个原因按三档说，档次决定用词：

- **有原文。** 作者写过为什么。说“因为”，并给出处，比如哪次提交、哪个文件哪一行。
- **推断。** 没人写过，是你根据几条线索推出来的。说“看起来是”或“可能是”，并说出是哪几条线索。
- **查不到。** 说清你查了哪些地方。

不能拿代码本身证明作者的意图。用户自己带的猜测，当成几种可能之一去查，不要顺着认。查完证据支持，就说支持并给出处。证据不支持，就说不支持，并写出证据实际指向什么。转述时不要把“推断”说成“因为”。

## 怎么讲

1. 先给最小的完整答案，两三句。先用一般说法讲它是什么，有通用名字就放在括号里。再落到这个项目：“在这里，它用来……”。
2. 紧接着走一遍眼前这次真实操作：用户做某个操作时，依次发生什么。这就是怎么运作。例子用项目里真实的一次操作。比方最多一句，帮新手抓住大意，紧接着回到项目里真实的一次操作。比方不能代替真实例子。只列函数名和常量是查阅资料，不是讲解。
3. 有容易误解的地方，用户多半会以为是一回事，实际是另一回事，就单独点出来，并说它会带来什么后果。没有这种地方就不写。
4. 然后停。边界情况、历史原因、更深的层次，等用户再要才写。用户这次问的就是原因时，两三句里用上面的三档把原因说清，不另开一长段。
5. 讲具体机制。不预告接下来要讲什么。不写“关键是”“核心在于”“这里是难点”这类标签。不出测验，不要求用户复述。
6. 三个以上部件时，不要一张图画全。有画图工具就分步加：先画前两个，再重画并加上下一个。代码里真有回流，再把返回的那条线加上。没有画图工具，就用文字按同样的顺序写。只有一个简单点时不画。
7. 用户回过来说自己的理解时，只判对错、补漏，不从头再讲。

写完按 [unslop](../unslop/SKILL.md) 的中文规则自查一遍。

## 回复

回复就是讲解本身，不汇报你查了什么、做了什么。开头是那两三句。用了比方就只有一句，紧接着是眼前这次真实操作。有容易误解的地方就单独点出，并说后果。然后停。
