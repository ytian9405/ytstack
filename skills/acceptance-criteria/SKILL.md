# 验收标准

写一份用户读完就能拍板的验收标准，在动手前定下什么算做完，让之后的实现无法靠自己宣布完成。这份标准就是本次的交付物：不写代码，不改项目文件；也不要声称标准已经验证过，它们还没有被运行。

## 先读项目

读 README、相关代码和现有测试，弄清现在实际能做什么、用户从哪个入口用它、哪些现有行为不能被弄坏。需求依赖项目里还不存在的东西时，这件事本身就要请用户决定。

## 分清谁来决定

产品决定属于用户：选法不同，用户看到的结果就不同，比如超时从哪一刻算起、重试几次、额度用完后任务变成什么。实现选择用户看不出差别，不写进标准，比如字段名、内部函数怎么拆。产品决定不要悄悄定死：每个都给推荐选项，按推荐写完整份标准，让用户一次看完、一次改完。只列真正改变结果的决定，最多 3 个。

## 写成一份规格说明

开头一句话说这次要做到什么，必要时带一句这次不做什么；然后是编号条目，每条写清做什么、应该看到什么、靠什么证据算通过。证据是实际运行的命令和结果、保存下来的内容，模拟和推断不算。多个边界情况可以并成一张小表。读者负责项目但不一定懂实现，全文用日常说法。目标约 900 字，最长 1200 字；宁可少几条，也不要把每条写成一段。

正文再按这个顺序补三块：

- 试听、看效果、批准这类只有用户本人能做的检查，单独列成条目，写明自动检查不能代替它。
- 现有行为里最容易被这次改动弄坏的几条，合并成一条“不能弄坏”，写短；内容来自你读到的 README 或代码，不要凭记忆。
- 最后放要用户拍板的事，最多 3 行，写成“已按推荐写进上面的条件，你可以改：……”，每行说清选另一个会有什么不同；决定更多时，其余按推荐处理，一句话列出。

## 交付前过四关

每条标准逐条检查，过不了就改：能判对错，两个人照着查结论相同，不出现“合理”“稳定”这类词；不绑定做法，换一种同样满足需求的实现仍能通过；想过常出错的地方，至少覆盖一次失败输入、一次边界值、一次重新打开后状态还在，没有持久化则除外；不自相矛盾，条目之间不打架。条数或字数超了，就合并抓同一种错误的条目。

最后一句写：确认后可以交给 create-test-skill 变成可运行的测试。
